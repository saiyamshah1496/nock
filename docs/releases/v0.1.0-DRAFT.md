## What Nock is / isn’t

- Nock is a pattern linter for Postgres DDL. It gates risky migrations in CI and MCP using your table sizes, Postgres lock classes, and a `lock_timeout` policy — and it never applies migrations.
- Nock isn’t a migration framework, runner, or apply tool. It produces a verdict JSON (pass/warn/fail) so humans and bots can decide to merge or adjust.

## Free modes

- Bring your own estate: commit `.nock/estate.json` and check PRs against it. See `docs/guides/quick-start-estate-file.md`.
- Sync estate yourself: generate `.nock/estate.json` from a read‑only role (prefer a replica) on your own runner. See `docs/guides/sync-estate.md` and `docs/guides/grants-sync-estate.md`.

## Surfaces (CLI ≡ Action ≡ MCP)

The CLI, GitHub Action, and MCP server return the same verdict JSON for the same inputs.
- CLI: `node packages/cli/dist/bin/nock.js check --sql <path> --estate <path> --format json`
- Action: see `examples/workflows/nock.yml` (CLI workflow) or `examples/workflows/nock-action.yml` (Action workflow)
- MCP: from source until npm (see below)

## MCP from-source (until npm publish)

Add this to your MCP host config (Cursor/Claude) and build the repo first:

```json
{
  "mcpServers": {
    "nock": {
      "command": "node",
      "args": ["./packages/mcp/dist/bin.js"]
    }
  }
}
```

After `pnpm build`, `node ./packages/mcp/dist/bin.js` starts a local MCP server that exposes:
- `check_before_apply` — returns verdict JSON for provided SQL and optional `estatePath` / `policyPath`
- `list_rules` — lists rule ids and defaults
- `explain_lock` — best‑effort lock mode for a statement
